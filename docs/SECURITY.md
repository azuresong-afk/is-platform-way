## 6. Разделение обязанностей

| Проверено | Результат |
|---|---|
| Администратор не меняет себе роли, проекты, статус и флаг администратора; не добавляет себя в команду с ролями и не меняет роли/проекты команды, где состоит | ✅ |
| Администратор платформы без рабочих ролей не видит вкладок продуктов | ✅ |
| Обходы: (а) сервисная учётная запись с ролями в продукте; (б) смена пароля другой записи, в том числе другого администратора, и вход под ней; (в) новая запись с ролями | 🔧 шаг 5.8, ниже |
| Пароль, заданный администратором (при создании записи или сбросе), — **временный** (`users.password_temporary`). С ним токен без ролей, проектов и прав администратора (`password_change_required: true`, контракт v1.1, п. 2.3), API платформы отвечает `403 password_change_required` везде, кроме `/me` и `POST /auth/password`; проверка по БД, поэтому сброс пароля действует и на уже выданный токен. Оболочка вместо кабинета показывает «Задайте свой пароль», продукт на `@platform/ui` уводит туда же. Смена: текущий пароль проверяется как при входе (неудачи ведут к блокировке), в шлюзе — тот же лимит частоты, что у входа; все сессии закрываются, выдаётся новая | ✅ `api/tests/test_sod.py`, `e2e/tests/sod.spec.ts` |
| Свой пароль администратор меняет только через «Сменить пароль» (`POST /auth/password`), не через `/admin/users/{id}/password` — иначе он сделал бы его временным себе | ✅ 403 |
| Журнал: у записи есть флаг `sod` — действие, которым администратор мог бы получить чужие роли. Помечаются: `user.password` (любой сброс чужого пароля); `user.roles` с непустыми ролями записи с временным паролем; `group.members`, если в команду с ролями или проектами добавлена запись с временным паролем; `group.roles`, если среди участников есть такая запись; `service_account.create`, `service_account.secret_rotate` и расширяющий `service_account.update` у включённой записи с ролями (секрет видит администратор); `auth.password_change` временного пароля с того же адреса, откуда его задал администратор (`details.same_ip_as_admin`). Экран «Журнал аудита» — флажок «Разделение обязанностей» (`GET /audit?sod=true`), пометка в строке и шторке; столбец `sod` в выгрузке | ✅ |
| Что остаётся: администратор, задавший временный пароль, может сам войти под записью и сменить его — тогда роли у записи заработают. Это не скрыто: сброс и роли такой записи помечены, а смена временного пароля с адреса администратора — тоже (подсказка: за общим NAT адрес совпадает и у честного пользователя). Настоящий пользователь узнает об этом при первом входе — его пароль не подойдёт | ⚖️ закрывает только (б) |
| (б) Второе подтверждение: роли новой записи и сервисной записи с ролями вступают в силу после одобрения другим администратором платформы (`SOD_TWO_PERSON`) | ⚖️ не делаем — решение владельца 06.11.2026; отложено (roadmap §7, вопрос 4) |

## 10. Зависимости

Шаг 5.10 (05.11.2026). Аудит теперь — задание `audit` в CI на каждый PR: `pip-audit` по файлам фиксированных версий, `npm audit --omit=dev` (должен быть чистым), `npm audit --audit-level=critical` (инструменты разработки) и `npm audit` в `e2e/`.

**Python.** Версии зафиксированы с хэшами: `api/requirements.lock` (образ API), `api/requirements-dev.lock` (то же + pytest и ruff, для CI), `dev/requirements.lock` (образ заглушек). Образы ставят пакеты с `--require-hashes --only-binary=:all:`: сборка повторяема, подменённый в зеркале пакет не установится, а поставка без интернета (5.3) берёт ровно эти версии. Пересобрать файл после правки `pyproject.toml` / `requirements.txt` — команда в заголовке файла; CI проверяет, что файлы не отстали. `pip-audit` по всем трём: **уязвимостей нет** (fastapi 0.162.0, starlette 1.10.0, uvicorn 0.54.0, SQLAlchemy 2.1.8, PyJWT 2.15.1, cryptography 50.0.2, httpx 0.28.1, python-multipart 0.0.33 и остальные).

**npm, то, что попадает в сборку** (`npm audit --omit=dev`): **уязвимостей нет**. `react-router-dom` 6.30 → 7.18 (п. 9): оболочке понадобилось только убрать флаги `future` у `BrowserRouter`; `@platform/ui` принимает `react-router-dom` `^6.20.0 || ^7.18.5`, так что продукты на 6 подключаются без правок.

## 11. Общий origin: принятые свойства архитектуры

- Все SPA (оболочка и продукты) живут на одном origin и читают один `sessionStorage['platform.token']`. XSS в любом продукте даёт его токен и вызов `/auth/refresh` с cookie. Защита — строгий CSP шлюза без `unsafe-inline` и вывод через React. ⚖️ это решение задания (один вход без повторной авторизации); продуктам при переходе — не ослаблять CSP.
- Ответ продукта может поставить cookie на весь origin (в том числе подменить `platform_refresh`). ⚖️ продукты — часть одной поставки и проверяются при подключении; токены платформы продуктам cookie не нужны.
- ~~Токен пользователя принимают и продукты, и API платформы (`aud` — все продукты + `platform`).~~ 🔧 Шаг 5.9 (контракт v1.1, п. 2.6): `aud` токена из `sessionStorage` — только продукты. Администрирование платформы (всё, что требует `platform_admin`, и чтение чужих проектов по этому флагу) принимает только токен оболочки `aud=["platform"]` на 5 минут; оболочка берёт его по refresh-cookie (`POST /auth/platform-token`, без ротации, с той же проверкой повторного предъявления) и держит в памяти вкладки, в продукты он не уходит. Проверено: `api/tests/test_platform_token.py`, `e2e/tests/platform-token.spec.ts` (токен из `sessionStorage` получает 401 на `/api/platform/admin/*`, в запросах к продуктам нет `aud=platform`).
- ⚖️ Что осталось. Бэкенд продукта с токеном пользователя по-прежнему может вызвать **другой** продукт (`aud` — все продукты, п. 2.1 контракта: иначе 401 вместо 403) и неадминистративные адреса платформы от имени этого пользователя (`/me`, свои проекты и их активы, уведомления) — в пределах прав самого пользователя. XSS на общем origin по-прежнему может взять токен оболочки через `/auth/platform-token`, как и сейчас `/auth/refresh` (первый пункт этого раздела): защита — CSP. Токены, выданные до обновления (`aud` с `platform`, до 15 минут), на администрирование не принимаются — оболочка сама берёт новый токен.
