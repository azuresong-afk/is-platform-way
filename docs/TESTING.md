# Ручная проверка этапа 1

Итог приёмки этапа 4.1 по этому списку и по общим критериям — [`ACCEPTANCE.md`](ACCEPTANCE.md); пункты, которые проверяются через браузер и HTTP, прогоняет `e2e/tests/acceptance.spec.ts`.

Стенд: `cp .env.example .env`, заполнить секреты, `COOKIE_SECURE=false`, затем `docker compose --profile fakes up --build`. Кабинет — http://127.0.0.1:18090/. Автотесты (`pytest`, `vitest`) проверяют то же на уровне кода, а сквозной сценарий единого входа (разделы 1, 3.2 и выход) прогоняет Playwright — см. [`e2e/README.md`](../e2e/README.md); этот список — для приёмки глазами.

## 5. Токены на стороне продуктов

Токен — из `sessionStorage` вкладки (DevTools → Application) или `POST /api/platform/auth/login`.

| # | Запрос | Ожидаемый результат |
|---|---|---|
| 5.1 | `curl :18090/api/vm/summary` без токена | 401 |
| 5.2 | Токен `petrov`, `GET /api/vm/summary?project=<его проект>` | 200 |
| 5.3 | Токен `petrov`, `GET /api/scanner/summary` | 403 `no_product_roles` |
| 5.4 | Токен `petrov`, `GET /api/vm/summary?project=<чужой проект>` | 403 `no_project_access` |
| 5.5 | `curl :18090/api/platform/.well-known/jwks.json` | Ключ `OKP`/`Ed25519` с `kid`; приватных полей нет |
| 5.6 | «Ключи подписи» → «Плановая смена» | В таблице ключ «Опубликован заранее», он уже есть в JWKS (5.5), а новый вход ещё подписан прежним `kid`; через 20 мин новый ключ «Подписывает», прежний «Выведен» и остаётся в JWKS 30 мин |
| 5.7 | «Срочная смена» с отметкой «Отозвать текущий ключ» | Прежний `kid` пропал из JWKS; открытые вкладки один раз обновляют сессию через refresh и продолжают работу; в журнале аудита — `keys.rotate_immediate` |
| 5.8 | Войти администратором, взять токен из `sessionStorage`, `GET /api/platform/admin/users` с ним | 401 `platform_token_required`; при этом экран «Пользователи и доступ» в оболочке работает: она ходит в API платформы с токеном `aud=["platform"]` из памяти вкладки (контракт v1.1, п. 2.6). Автоматически: `e2e/tests/platform-token.spec.ts` |

## 8. Шина событий (этап 2.3)

Отправка тестового события: `python dev/send_event.py --product scanner --secret "$SCANNER_EVENTS_SECRET" --type scanner.run.finished` (адрес по умолчанию — шлюз `:18090`).

| # | Действие | Ожидаемый результат |
|---|---|---|
| 8.1 | Отправить событие | `202 {"accepted":true}`; в «Администрирование → События» строка «Сканер · scanner.run.finished» |
| 8.2 | Повторить с тем же `--id <id>` | `200 {"duplicate":true}`, второй строки нет |
| 8.3 | Отправить с `--secret wrong` | `401 bad_signature`; в `audit_log` запись `event.receive` с результатом `denied` |
| 8.4 | «Подписки продуктов» | «Устранение» и «Аттестация» подписаны на `scanner.run.finished`, «Сканер» — на `vm.remediation.verified`; все три — на `platform.keys.rotated`, `platform.project.updated` и `platform.user.blocked`; «Демо» — только на `platform.user.blocked` |
| 8.5 | После 8.1 открыть событие | Доставка «Устранению» и «Аттестации» — «Доставлено» |
| 8.6 | `docker compose stop fake-grc`, отправить событие | Доставка «Аттестации» — «Повтор», текст ошибки, время следующей попытки ≈ через 1 мин; фильтр «С ошибками доставки» показывает событие |

## 9. Комплект и восстановление из копии (шаги 3.4, 5.2)

Автоматически: `dev/suite-restore-check.sh` (нужны Docker, `curl`, `openssl`, `python3`; 5–10 минут, из них большая часть — сборка образов). Сценарий использует свои порты (28090/28010/25440) и свой временный `.env`, рабочую установку не трогает; `KEEP=1` оставляет восстановленный стенд запущенным, `NO_BUILD=1` — не пересобирать образы.

| # | Шаг | Ожидаемый результат |
|---|---|---|
| 9.1 | Стенд A: комплект на заглушках `scanner,vm,grc` | Все сервисы healthy; каждая заглушка пишет в свою базу своим пользователем |
| 9.2 | Администратор создаёт проект и пользователя с ролями во всех продуктах | Пользователь входит один раз, `/api/<id>/summary` всех продуктов отвечают 200 |
| 9.3 | `deploy/backup.sh` | `platform.dump`, `scanner.dump`, `vm.dump`, `grc.dump`, `globals.sql`, `MANIFEST` |
| 9.4 | Стенд A удаляется вместе с томами, `deploy/restore.sh` на новом стенде B | Восстановление без ошибок, комплект запускается |
| 9.5 | Проверки на B | Вход с прежним паролем; проект и роли на месте; те же `kid` в JWKS; токен, выданный на A, принимается продуктами B; данные продуктов на месте |
| 9.6 | Права в кластере B | Пользователи `platform`/`<id>` без SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS, каждый — владелец своей базы; `scanner` не подключается к `vm`, `platform`, `postgres` |

| 9.7 | `deploy/restore.sh` без `--yes` на базах с данными | Не в терминале — отказ «уже содержат данные; запустите с --yes»; в терминале — вопрос «Продолжить? [y/N]», ответ «n» — «отменено». Комплект продолжает работать, данные на месте |
| 9.8 | Испорченный `.dump` (байт заменён, SHA-256 не совпадает с `MANIFEST`) | «контрольные суммы не сходятся» до остановки комплекта и удаления баз; ни одна база не тронута |
| 9.9 | `deploy/backup.sh --offline` | Останавливает все приложения, кроме `db`, на время копии и запускает обратно; в `MANIFEST` — `offline=1`; копия всех баз из `PLATFORM_PRODUCTS` |
| 9.10 | `deploy/restore.sh <копия> --only <id>` (последний продукт из `PLATFORM_PRODUCTS`) | Заменяется только база `<id>`, остальные базы не тронуты; комплект запущен, продукт отвечает |

Пункты 9.7–9.10 (шаг 5.2) проверяет тот же `dev/suite-restore-check.sh` на стенде B после восстановления; список баз он берёт из `PLATFORM_PRODUCTS` стенда.
