# Установка и сопровождение

## Требования

- Linux-сервер, Docker Engine 24+ с плагином `docker compose`.
- 2 vCPU, 4 ГБ ОЗУ, 20 ГБ диска для платформы (без продуктов).
- Открытый наружу порт шлюза: 18090 (http) и/или 18443 (https). API и БД публикуются только на `127.0.0.1`.

## Первая установка

```bash
git clone <репозиторий> platform && cd platform
cp .env.example .env
```

Заполните в `.env`:

| Переменная | Как получить |
|---|---|
| `PLATFORM_SECRET_KEY` | `openssl rand -base64 32` — ключ шифрования приватных ключей подписи. **Потеря ключа = перевыпуск ключей подписи и повторный вход всех пользователей.** Храните отдельно от резервных копий БД. |
| `PLATFORM_DB_PASSWORD` | любой длинный пароль |
| `BOOTSTRAP_ADMIN_PASSWORD` | пароль первого администратора; используется, только пока в БД нет пользователей |
| `PLATFORM_PRODUCTS` | id продуктов установки через запятую, по умолчанию `scanner,vm,grc`; порядок — порядок вкладок |
| `<ID>_API_UPSTREAM` | внутренний адрес API продукта, например `http://scanner-app:8000`; пусто — продукта нет в кабинете |
| `<ID>_WEB_UPSTREAM` | адрес web-контейнера продукта (SPA собрана с `VITE_BASE=/<id>/`) |
| `<ID>_EVENTS_SECRET` | `openssl rand -hex 32`, свой на каждый продукт; тот же секрет задаётся продукту в `PLATFORM_EVENTS_SECRET` |
| `<ID>_LARGE_UPLOAD_PATHS`, `<ID>_LARGE_UPLOAD_MAX_BODY` | пути API продукта с большим телом запроса и лимит для них (у «Сканера» — загрузка БДУ, `512m`) |
| `PLATFORM_GATEWAY_BIND` | `0.0.0.0`, чтобы шлюз был доступен из сети |

Продукты должны быть в одной docker-сети со шлюзом и API. Проще всего подключить их к сети платформы (`platform_default`) как внешнюю сеть в их compose-файле, или указать адреса, доступные с хоста.

Запуск:

```bash
docker compose up -d --build
docker compose ps          # все сервисы healthy/running
docker compose logs -f platform-api
```

При старте API проверяет секреты (ключ — ровно 32 байта, секреты событий подключённых продуктов — не короче 16 символов), применяет миграции и создаёт первого администратора. Ошибка в секретах — контейнер останавливается с понятным сообщением в логе.

## Подключение нового продукта

Платформа не содержит списка продуктов в коде: продукт подключается правкой `.env`, без сборки платформы (roadmap §1а).

1. Продукт выполняет контракт v1 (раздел «Контракт платформы v1» в `docs/spec/03-platforma.md`) с уточнениями `docs/contract-v1.1.md`: отдаёт `GET /manifest` и `GET /health/ready`, проверяет JWT платформы по JWKS, по желанию — `/summary` в общем формате `data.kpis[]` (п. 10.1), `/search` и приём событий.
2. Выберите id: строчные латинские буквы и цифры, 2–20 символов, первая — буква (например, `demo`). Нельзя: `platform`, `api`, `admin`, `login`, `assets`, `fonts`. Id становится адресом `/<id>/`, префиксом API `/api/<id>/`, значением `aud` в токене и префиксом переменных (`DEMO_…`).
3. В `.env` платформы:

   ```bash
   PLATFORM_PRODUCTS=scanner,vm,grc,demo
   DEMO_API_UPSTREAM=http://demo-app:8000     # внутренний адрес API продукта
   DEMO_WEB_UPSTREAM=http://demo-web:8080     # web-контейнер (SPA с VITE_BASE=/demo/); можно пусто
   DEMO_EVENTS_SECRET=<openssl rand -hex 32>  # то же значение — продукту в PLATFORM_EVENTS_SECRET
   # по желанию: пути с большими загрузками и лимит для них
   # DEMO_LARGE_UPLOAD_PATHS=/imports/upload
   # DEMO_LARGE_UPLOAD_MAX_BODY=1g
   ```

4. Подключите контейнеры продукта к сети платформы (`platform_default`) и перезапустите платформу: `docker compose up -d`.

Что появится само:

- маршруты шлюза `/api/demo/` и `/demo/`;
- продукт в «Администрирование → Продукты»; до первого ответа продукта — с минимальным манифестом без ролей, после — с названием, иконкой и ролями из манифеста (опрос раз в минуту или кнопка «Проверить»);
- роли продукта в «Пользователях» и в сервисных учётных записях, `demo` в `aud` токена;
- вкладка и карточка на Главной у пользователей с ролями продукта (карточка рисуется по `data.kpis[]`); поиск Ctrl+K по `search_url`.

Порядок вкладок — по числу `order` в манифесте, если продукт его задаёт, иначе по месту id в `PLATFORM_PRODUCTS`.

Проверка на заглушке: `fake-demo` из профиля `fakes` — четвёртый продукт, о котором платформа ничего не знает заранее. Добавьте `demo` в `PLATFORM_PRODUCTS`, задайте `DEMO_API_UPSTREAM=http://fake-demo:8000` и `DEMO_EVENTS_SECRET`, затем `docker compose --profile fakes up -d --build`.

Отключение: уберите id из `PLATFORM_PRODUCTS` (или очистите `<ID>_API_UPSTREAM`) и перезапустите. Продукт пропадёт из кабинета и из `aud`; выданные роли сохраняются в БД и вернутся при повторном подключении.

## Обновление

```bash
git pull
docker compose up -d --build
```

Миграции применяются автоматически при старте API. Перед обновлением сделайте резервную копию БД (ниже). Откат версии с откатом схемы не поддерживается — восстанавливайтесь из копии.

## Резервное копирование и восстановление

Для отдельной установки платформы (`docker-compose.yml`, одна база `platform`):

```bash
docker compose exec -T db pg_dump -U platform -Fc platform > platform-$(date +%F).dump
```

Восстановление в пустую БД:

```bash
docker compose stop platform-api gateway
docker compose exec -T db dropdb -U platform platform
docker compose exec -T db createdb -U platform platform
docker compose exec -T db pg_restore -U platform -d platform --no-owner < platform-2026-11-04.dump
docker compose start platform-api gateway
```

Для комплекта — скрипты `deploy/backup.sh` и `deploy/restore.sh`, см. раздел «Комплект». В обоих случаях копия содержит хеши паролей, зашифрованные ключи подписи и журнал аудита; для восстановления нужен тот же `PLATFORM_SECRET_KEY`, что был при создании копии. Журнал аудита защищён триггером от изменения и удаления строк; восстановление в пустую БД этим не затрагивается.

## Комплект: платформа и продукты

`docker-compose.suite.yml` поднимает всю связку на одном сервере: шлюз, платформу и продукты из `PLATFORM_PRODUCTS` в режиме `AUTH_MODE=platform`, с одним кластером PostgreSQL 16. Отдельная установка платформы (`docker-compose.yml`) остаётся для случая, когда продукты живут на своих серверах.

### Что внутри

| Сервис | Что делает |
|---|---|
| `gateway`, `platform-api`, `platform-web` | платформа, как в отдельной установке |
| `db` | один кластер PostgreSQL; наружу — только `127.0.0.1:${PLATFORM_DB_PORT}` |
| `db-init` | при каждом запуске создаёт недостающие базы и пользователей, приводит пароли и права к `.env`, завершается |
| `<id>-app` | API продукта из образа `<ID>_IMAGE` (порт 8000, наружу не публикуется) |
| `<id>-web` | SPA продукта из `<ID>_WEB_IMAGE`, если задан |

Продукты не перечислены в compose-файле: `deploy/suite.sh` читает `.env` и генерирует `deploy/.generated/suite.products.yml` (сервисы продуктов, их переменные для шлюза и API, пароли баз для `db-init`). Поэтому комплект запускается **только через `deploy/suite.sh`** — это обычный `docker compose` с нужными `-f`, все его команды работают так же.

### Базы и права

| База | Пользователь | Права |
|---|---|---|
| `platform` | `platform` | владелец своей базы, подключение только к ней |
| `<id>` для каждого продукта | `<id>` | то же |
| `postgres` (служебная) | `postgres` | суперпользователь; его пароль `POSTGRES_SUPERUSER_PASSWORD` получают только `db`, `db-init` и скрипты копирования, приложениям он не передаётся |

У пользователей приложений нет `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION`, `BYPASSRLS`; `CONNECT` к каждой базе отозван у `PUBLIC`, так что продукт не может подключиться ни к чужой базе, ни к служебной. Пароль в `.env` поменяли — при следующем `deploy/suite.sh up` `db-init` применит его в кластере (перезапустите и приложение, которому он принадлежит). Продукт убрали из `PLATFORM_PRODUCTS` — его база и пользователь остаются; удалите их вручную, если данные не нужны.

### Установка

```bash
cp .env.suite.example .env
```

1. `PLATFORM_PRODUCTS` — какие продукты в установке (`scanner,vm,grc` или часть из них).
2. Секреты платформы: `PLATFORM_SECRET_KEY` (`openssl rand -base64 32`), `POSTGRES_SUPERUSER_PASSWORD`, `PLATFORM_DB_PASSWORD`, `BOOTSTRAP_ADMIN_PASSWORD`.
3. Для каждого продукта: `<ID>_IMAGE` и, если есть, `<ID>_WEB_IMAGE` (имя образа с тегом из вашего реестра), `<ID>_DB_PASSWORD`, `<ID>_EVENTS_SECRET` (`openssl rand -hex 32`). Пароли БД — только латиница и цифры (они попадают в `DATABASE_URL`), не короче 16 символов: `openssl rand -hex 24`.
4. Собственные настройки продукта (его секреты, лимиты) — в `deploy/env/<id>.env` по образцу `deploy/env/example.env`.

```bash
deploy/suite.sh build             # образы платформы из этого репозитория (или задайте PLATFORM_*_IMAGE)
deploy/suite.sh pull              # образы продуктов из реестра
deploy/suite.sh up -d --wait      # запуск; --wait ждёт, пока все сервисы станут healthy
deploy/suite.sh ps
deploy/suite.sh logs -f scanner-app
```

Каждый продукт получает `AUTH_MODE=platform`, `DATABASE_URL` своей базы, `PLATFORM_URL`, `PLATFORM_JWKS_URL`, `PLATFORM_EVENTS_URL`, `PLATFORM_EVENTS_SECRET` и `PLATFORM_PRODUCT_ID` (контракт v1.1, п. 12). Адреса продуктов для шлюза и API по умолчанию — сервисы комплекта (`http://<id>-app:8000`, `http://<id>-web:8080`); задавать `<ID>_API_UPSTREAM` нужно, только если продукт работает вне комплекта.

Новый продукт: id в `PLATFORM_PRODUCTS`, переменные `<ID>_IMAGE`, `<ID>_DB_PASSWORD`, `<ID>_EVENTS_SECRET` в `.env`, затем `deploy/suite.sh up -d --wait` — `db-init` создаст его базу, шлюз — маршруты. Свои дополнения к compose (тома, лимиты ресурсов) — в `deploy/docker-compose.suite.override.yml`, он подключается автоматически.

Обновление: смените теги образов в `.env`, сделайте копию (`deploy/backup.sh`), затем `deploy/suite.sh pull && deploy/suite.sh up -d --wait`. Миграции платформы и продуктов выполняются при старте их контейнеров.

### Резервная копия

```bash
deploy/backup.sh                  # → backups/<UTC-время>/, все базы кластера
deploy/backup.sh --offline        # остановить приложения на время копии — все базы на один момент
BACKUP_KEEP=14 deploy/backup.sh   # и оставить 14 последних копий в backups/
```

В каталоге копии: `<база>.dump` (`pg_dump -Fc`) для `platform` и каждого продукта, `globals.sql` (роли без паролей, для справки) и `MANIFEST` с версией PostgreSQL и контрольными суммами SHA-256. Без `--offline` каждая база согласована сама с собой, но между базами возможен разрыв в секунды (например, событие уже в журнале платформы, а в базе продукта — ещё нет); для копии перед обновлением используйте `--offline`.

**В копии нет `.env` и `deploy/env/*.env`.** Без `PLATFORM_SECRET_KEY` из копии не восстановить ключи подписи (все пользователи войдут заново после перевыпуска ключей), без паролей — не подключиться к базам. Храните `.env` отдельно от копий, в хранилище секретов.

Пример ежедневной копии в cron пользователя, который может запускать docker:

```
30 2 * * * cd /opt/platform && BACKUP_KEEP=14 deploy/backup.sh >> /var/log/platform-backup.log 2>&1
```

### Восстановление

```bash
deploy/restore.sh backups/20261104T023000Z             # все базы из копии
deploy/restore.sh backups/20261104T023000Z --only vm   # только база «Устранения»
```

Скрипт проверяет контрольные суммы, при непустых базах спрашивает подтверждение (`--yes` — без вопроса), останавливает всё, кроме `db`, пересоздаёт восстанавливаемые базы через `db-init`, выполняет `pg_restore` **от имени пользователя продукта** (владелец объектов — он, а не `postgres`) и запускает комплект (`--no-start` — не запускать).

**На чистом стенде** (новый сервер или после потери тома):

1. Разверните репозиторий той же или более новой версии, положите `.env` (тот же `PLATFORM_SECRET_KEY`, та же совокупность `PLATFORM_PRODUCTS`; пароли БД могут быть новыми) и `deploy/env/*.env`.
2. Скопируйте каталог копии на сервер.
3. `deploy/suite.sh build && deploy/suite.sh pull` (или загрузите образы из своего реестра).
4. `deploy/restore.sh <каталог копии>` — не запускайте комплект до восстановления, иначе API создаст первого администратора в пустой базе (скрипт это переживёт, но пустая база будет заменена копией).

После восстановления пользователи входят с прежними паролями, ключи подписи прежние (выданные до сбоя токены продолжают действовать до истечения срока), проекты, роли, журнал аудита и данные продуктов — на момент копии. Если версия платформы или продукта новее копии, их миграции доведут схему при старте.

Проверка всей процедуры на заглушках продуктов — `dev/suite-restore-check.sh` (см. `docs/TESTING.md`): поднимает комплект, создаёт данные, делает копию, удаляет стенд вместе с томами, восстанавливает на новом и проверяет вход, проекты, ключи, данные продуктов и права пользователей БД. Тот же сценарий выполняется в CI.

## TLS

Шлюз включает https на порту 8443 (снаружи — `PLATFORM_GATEWAY_TLS_PORT`, по умолчанию 18443), когда заданы `TLS_CERT` и `TLS_KEY`. Тогда http-порт отвечает редиректом на https (кроме `/healthz`).

1. Положите файлы в `deploy/tls/` (или каталог из `TLS_DIR`):
   - `fullchain.pem` — сертификат сервера **и все промежуточные сертификаты** по порядку;
   - `privkey.pem` — закрытый ключ без пароля; шлюз работает под uid 101, поэтому либо `chown 101 privkey.pem && chmod 600 privkey.pem`, либо `chmod 640` с группой 101.
2. В `.env`:
   ```
   TLS_CERT=/etc/nginx/tls/fullchain.pem
   TLS_KEY=/etc/nginx/tls/privkey.pem
   SERVER_NAME=platform.example.ru
   COOKIE_SECURE=true
   ```
3. `docker compose up -d gateway` и проверка: `openssl s_client -connect platform.example.ru:18443 -servername platform.example.ru </dev/null | grep -E 'Verify return|subject|issuer'`.

### Сертификаты российских УЦ

Сертификат, выданный УЦ Минцифры (НУЦ), подписан промежуточным «Russian Trusted Sub CA», который подписан корневым «Russian Trusted Root CA».

- В `fullchain.pem` кладите сертификат сервера, затем промежуточный «Russian Trusted Sub CA». Корневой сертификат в цепочку не включают.
- Браузеры и ОС клиентов должны доверять «Russian Trusted Root CA». Его ставят в хранилище ОС (Windows — «Доверенные корневые центры сертификации», Linux — `/usr/local/share/ca-certificates/` + `update-ca-certificates`) или используют браузеры, где он уже есть (Яндекс Браузер, Атом). Сертификаты берутся с портала Госуслуг (раздел «Сертификаты безопасности»).
- Если API продуктов обращаются к платформе по https (например, за JWKS), в их контейнеры тоже нужно добавить корневой сертификат. Внутри docker-сети рекомендуется ходить по http напрямую к `platform-api:8000`, как в `docker-compose.yml`.
- Внутренний корпоративный УЦ работает так же: промежуточные — в `fullchain.pem`, корневой — в доверенные у клиентов.

Без TLS (только для стенда) задайте `COOKIE_SECURE=false`, иначе браузер не сохранит cookie обновления сессии и после перезагрузки страницы потребуется повторный вход.

## Перенос пользователей и проектов «Сканера»

Одноразовая утилита читает БД «Сканера» (только чтение) и переносит пользователей с паролями, роли «Сканера» и проекты (`engagement`). Полная процедура перехода — в `docs/MIGRATION.md` (этап 3).

```bash
# пробный запуск: отчёт о том, что будет сделано, без записи
docker compose exec platform-api python -m app.cli import-scanner \
  --source 'postgresql+psycopg://scanner_ro:...@scanner-db:5432/scanner'
# запись + файлы соответствий
docker compose exec platform-api python -m app.cli import-scanner --source '...' --apply --out /tmp/scanner-import
docker compose cp platform-api:/tmp/scanner-import ./scanner-import
```

- Пароли переносятся как есть (формат scrypt «Сканера» платформа понимает) и перехэшируются при первом входе. Пользователь с хэшем другого формата переносится без пароля — задайте его в «Пользователи».
- Права в «Сканере» глобальные, поэтому новые пользователи получают «все проекты»; существующим пользователям платформы добавляется участие в перенесённых проектах.
- Администраторы «Сканера» не становятся администраторами платформы, пока не указан `--grant-platform-admin`.
- Повторный запуск безопасен: уже перенесённые проекты не дублируются, у пользователей синхронизируются роли «Сканера», пароль и профиль не меняются.
- `scanner-link-projects.sql` выполняется в БД «Сканера» после его миграции, добавившей `engagement.platform_project_id`; `mapping.json` — соответствие id «Сканера» → id платформы.
- Если таблицы или столбцы называются иначе, утилита покажет, что нашла, а имя задаётся явно: `--map users.username=login`, `--map engagements.table=projects`.

## Порты

| Порт хоста | Сервис | Привязка |
|---|---|---|
| 18090 | шлюз, http | `PLATFORM_GATEWAY_BIND` (по умолчанию 127.0.0.1) |
| 18443 | шлюз, https | `PLATFORM_GATEWAY_BIND` |
| 18010 | API платформы (отладка) | 127.0.0.1 |
| 15440 | PostgreSQL (отладка) | 127.0.0.1 |

В комплекте порты те же; продукты наружу не публикуются, к ним ходят только через шлюз.

## Журналы

Логи контейнеров ротируются (json-file, 5 × 10 МБ). Секреты, токены и пароли в журналы не пишутся. Действия пользователей — в журнале аудита в БД (таблица `audit_log`).

## Частые проблемы

| Признак | Причина |
|---|---|
| После обновления страницы снова экран входа | `COOKIE_SECURE=true` при работе по http |
