# Переход установки «Сканера» на платформу

Инструкция для администратора, у которого «Сканер» уже работает отдельно (`AUTH_MODE=local`, свой вход), а теперь его нужно открыть вкладкой в «Платформе» с единым входом.

Порядок: **подготовка → резервные копии → пробный импорт → импорт → привязка проектов → включение `AUTH_MODE=platform` → проверки**. Если проверки не прошли — **откат** (последний раздел). Вся процедура отрепетирована на стенде с заглушками: [`dev/scanner-legacy/rehearse.sh`](../dev/scanner-legacy/rehearse.sh) проходит все шаги ниже и сверяет результат.

## Что переносится, а что нет

| Что | Куда | Как |
|---|---|---|
| Пользователи «Сканера»: имя входа, ФИО, почта, активность | в платформу | копируются; имя входа приводится к нижнему регистру |
| Пароли | в платформу | хэш scrypt «Сканера» копируется как есть, пароли пользователей не меняются; при первом входе платформа перехэширует пароль с текущими параметрами |
| Роли «Сканера» (`admin`, `operator`, `auditor`) и надбавки (`cred_audit`, `host_credentials`) | в платформу, роли продукта `scanner` | копируются; роль не из этого списка пропускается с предупреждением |
| Проекты (`engagement`) | в платформу | создаются проекты с теми же названием, заказчиком, номером договора и статусом; связь хранится в платформе и в столбце `engagement.platform_project_id` «Сканера» |
| Прогоны, находки, активы, allowlist, журнал аудита «Сканера» | остаются в БД «Сканера» | не копируются и не меняются |

Утилита импорта открывает БД «Сканера» **только на чтение**. В БД «Сканера» меняется одно: столбец `engagement.platform_project_id` заполняется на шаге 4 по готовому SQL-файлу.

Права в «Сканере» глобальные (роль действует во всех проектах), поэтому перенесённые пользователи получают доступ ко «всем проектам» платформы, как было. Сузить доступ можно потом в «Администрирование → Пользователи и доступ».

## Что изменится для пользователей

- Вход — на странице платформы `https://<адрес платформы>/login`, логин и пароль те же, что были в «Сканере». «Сканер» открывается вкладкой `/scanner/`; своей страницы входа у него больше нет.
- Пароль меняется и сбрасывается в платформе. Блокировка, отзыв ролей и доступ к проектам — тоже в платформе («Администрирование → Пользователи и доступ»).
- История «Сканера» на месте: прогоны, находки и записи журнала остаются за теми же людьми (см. «Как „Сканер“ узнаёт своих пользователей»).
- Интеграции, которые ходили в API «Сканера» по его собственному токену (`POST /auth/token` «Сканера»), перестанут работать. Для них заводится сервисная учётная запись платформы («Администрирование → Сервисные учётные записи», контракт v1.1, п. 2.2).

Простой «Сканера» — от остановки на шаге 1 до конца проверок, обычно 20–40 минут. Предупредите пользователей заранее.

## Как «Сканер» узнаёт своих пользователей

В режиме `platform` «Сканер» получает токен платформы, где пользователь назван `sub` (uuid платформы) и `preferred_username` (имя входа). При первом запросе с неизвестным `sub` «Сканер» ищет своего пользователя с тем же именем входа и привязывает к нему `sub`; не находит — создаёт новую теневую запись. Это правило — контракт v1.1, п. 2.5.

Отсюда главное требование к импорту: **одно имя входа — один человек и в «Сканере», и в платформе.** Утилита переносит имена как есть. Если в платформе уже есть пользователь с таким же логином (чаще всего первый администратор `admin`), утилита не создаёт второго, а добавляет роли «Сканера» существующей учётной записи. Пароль у неё остаётся платформенный. Пробный запуск показывает такие логины строкой «Уже есть в платформе…» — разберите её до `--apply` (шаг 2).

## Требования

1. **Платформа установлена и работает** по [`docs/INSTALL.md`](INSTALL.md): вход администратора, вкладки других продуктов, `docker compose ps` — всё `healthy`.
   - Первый администратор платформы (`BOOTSTRAP_ADMIN_USERNAME`) **не должен совпадать** ни с одним логином «Сканера». Удобно `platform-admin`. Если платформа уже поставлена с `admin`, а в «Сканере» тоже есть `admin`, — см. шаг 2.
2. **Версия «Сканера» с режимом платформы**: в ней сделаны пункты раздела «Что сделать каждому продукту → „Сканер“» контракта [v1.1](contract-v1.1.md): `AUTH_MODE=platform`, привязка пользователей по п. 2.5, миграция `engagement.platform_project_id`, `GET /manifest`, `/summary`, `/search`, события, фронтенд с `VITE_BASE=/scanner/`. Переменные окружения этой версии — в `docs/integration/scanner.md`.
3. **Общая docker-сеть.** Контейнеры `app` и `web` «Сканера» должны видеть `platform-api` и быть видны шлюзу. В compose-файле «Сканера» подключите их к сети платформы (по умолчанию `platform_default`, если каталог платформы называется `platform`):
   ```yaml
   # docker-compose.override.yml «Сканера»
   services:
     app: { networks: [default, platform] }
     web: { networks: [default, platform] }
   networks:
     platform: { external: true, name: platform_default }
   ```
   Имена сервисов дальше: `scanner-app` и `scanner-web` — сетевые псевдонимы, которые видит платформа. Если compose-проект «Сканера» называется `scanner`, контейнеры доступны как `scanner-app-1` / `scanner-web-1`; задайте псевдонимы явно (`aliases: [scanner-app]`) или подставьте свои имена.
4. **Окно работ** согласовано, пользователи предупреждены.

Ниже: каталог платформы — `/opt/platform`, каталог «Сканера» — `/opt/scanner`, сервисы «Сканера» — `app`, `web`, `db`, база и её владелец — `scanner`. Подставьте свои.

## Шаг 0. Подготовка (можно накануне)

**0.1. Обновите «Сканер» до версии с режимом платформы, оставив `AUTH_MODE=local`.** Так обновление и переключение — два отдельных шага, и при проблеме понятно, что сломалось. Перед обновлением — копия БД по шагу 1. Миграции «Сканера» добавят `engagement.platform_project_id`; «Сканер» работает как раньше.

**0.2. Пользователь БД «Сканера» только на чтение** для утилиты импорта:

```bash
cd /opt/scanner
docker compose exec -T db psql -U scanner -d scanner <<'SQL'
CREATE ROLE scanner_ro LOGIN PASSWORD 'длинный-пароль';
GRANT CONNECT ON DATABASE scanner TO scanner_ro;
GRANT USAGE ON SCHEMA public TO scanner_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO scanner_ro;
SQL
```

Утилите нужны только таблицы пользователей, ролей и проектов (`users`, `user_permissions`/`user_roles`, `engagements`); можно выдать `SELECT` только на них.

**0.3. Доступ платформы к БД «Сканера» на время импорта.** Утилита запускается в контейнере `platform-api`, поэтому БД «Сканера» временно подключается к сети платформы:

```bash
docker network connect --alias scanner-db platform_default $(cd /opt/scanner && docker compose ps -q db)
```

**0.4. Пробный запуск (шаг 2) можно сделать уже сейчас** — он ничего не пишет. Так все вопросы по логинам и ролям решаются до окна работ.

## Шаг 1. Резервные копии

Остановите приложение «Сканера», чтобы данные не менялись (БД остаётся работать):

```bash
cd /opt/scanner && docker compose stop web app
```

Снимите копии обеих БД и сохраните `.env` обоих продуктов:

```bash
mkdir -p /opt/backup/migration && cd /opt/backup/migration
(cd /opt/scanner  && docker compose exec -T db pg_dump -U scanner  -Fc scanner)  > scanner-before.dump
(cd /opt/platform && docker compose exec -T db pg_dump -U platform -Fc platform) > platform-before.dump
cp /opt/scanner/.env scanner.env.before && cp /opt/platform/.env platform.env.before
```

Убедитесь, что копии читаются (в выводе есть данные таблицы пользователей):

```bash
(cd /opt/scanner && docker compose exec -T db pg_restore -l) < scanner-before.dump | grep 'TABLE DATA'
(cd /opt/platform && docker compose exec -T db pg_restore -l) < platform-before.dump | grep 'TABLE DATA'
```

Копии содержат хэши паролей — храните их так же, как сами БД. Для восстановления платформы нужен тот же `PLATFORM_SECRET_KEY`.

## Шаг 2. Пробный запуск импорта

```bash
cd /opt/platform
docker compose exec platform-api python -m app.cli import-scanner \
  --source 'postgresql+psycopg://scanner_ro:длинный-пароль@scanner-db:5432/scanner'
```

Без `--apply` ничего не записывается. Пример вывода (стенд):

```
Столбцы источника:
  users.table                  users
  users.username               username
  users.password               password_hash
  users.roles                  role
  roles.table                  user_permissions
  engagements.table            engagements
  engagements.status           status
  …
Итог (пробный запуск, ничего не записано; добавьте --apply):
  users_created                5
  users_updated                0
  users_unchanged              0
  users_without_password       1
  projects_created             3
  projects_existing            0

Администраторы «Сканера»: sidorova, admin
  Права администратора платформы не выданы (--grant-platform-admin).

Без пароля (задать в «Пользователи»): old
Предупреждение: old: хэш пароля не в формате scrypt — нужен новый пароль
```

Что проверить:

| Строка | Что значит | Что делать |
|---|---|---|
| «Столбцы источника» | какие таблицы и столбцы утилита нашла сама | `—` у обязательного (`users.username`, `users.password`, `engagements.name`) — укажите имя явно: `--map users.username=login`, `--map engagements.table=projects`. Ключи `--map` — те же, что в этом списке |
| `users_created`, `projects_created` | сколько будет создано | сверьте с числом пользователей и проектов в «Сканере» |
| «Уже есть в платформе, получат роли „Сканера“…» | такой логин в платформе уже есть | если это **тот же человек** — ничего не делать, его пароль останется платформенным. Если **другой** (типично: `admin` платформы и `admin` «Сканера») — переименуйте одного из них **до импорта**: в «Сканере» (`UPDATE users SET username='scanner-admin' WHERE username='admin'`, пока он в режиме `local`) или в платформе. Иначе история «Сканера» привяжется не к тому человеку |
| «Администраторы „Сканера“» | у кого роль `admin` «Сканера» | права администратора **платформы** они не получают. Нужны — добавьте `--grant-platform-admin` на шаге 3 или выдайте вручную. Помните: администратор платформы не может выдать роли самому себе |
| «Без пароля» | хэш не в формате scrypt или пустой | такие пользователи переносятся без пароля; пароль задаётся в «Пользователи и доступ» после импорта |
| «Неизвестные роли у …» | роль, которой нет у «Сканера» в платформе | роль пропускается; при необходимости выдайте подходящую вручную |
| `users_updated` / `projects_existing` при первом запуске | что-то уже переносили | нормально для повторного запуска; при первом — разберитесь, откуда данные |

Отключённые в «Сканере» пользователи переносятся отключёнными и войти не могут.

## Шаг 3. Импорт

```bash
cd /opt/platform
docker compose exec platform-api python -m app.cli import-scanner \
  --source 'postgresql+psycopg://scanner_ro:длинный-пароль@scanner-db:5432/scanner' \
  --apply --out /tmp/scanner-import          # [--grant-platform-admin]
docker compose cp platform-api:/tmp/scanner-import /opt/backup/migration/
```

В `/opt/backup/migration/scanner-import/`:

- `mapping.json` — соответствие id «Сканера» → uuid платформы для пользователей и проектов. Сохраните вместе с копиями;
- `scanner-link-projects.sql` — SQL для шага 4.

Повторный запуск безопасен: проекты не дублируются, у пользователей синхронизируются роли «Сканера», пароль и профиль не меняются. Если после импорта в «Сканере» что-то поменяли (новый проект, новый пользователь), просто запустите шаг 3 ещё раз и возьмите новый SQL-файл. В журнале аудита платформы каждый запуск с `--apply` оставляет запись `import.scanner` с итогами.

## Шаг 4. Привязка проектов в БД «Сканера»

```bash
cd /opt/scanner
docker compose exec -T db psql -U scanner -d scanner -v ON_ERROR_STOP=1 \
  < /opt/backup/migration/scanner-import/scanner-link-projects.sql
docker compose exec -T db psql -U scanner -d scanner \
  -c 'select id, name, platform_project_id from engagements order by id'
```

Ожидается: у каждого проекта заполнен `platform_project_id`, значения совпадают с `engagements` в `mapping.json`. Ошибка `column "platform_project_id" does not exist` — «Сканер» не обновлён до нужной версии (шаг 0.1).

Временный доступ к БД больше не нужен:

```bash
docker network disconnect platform_default $(cd /opt/scanner && docker compose ps -q db)
```

## Шаг 5. Включение `AUTH_MODE=platform`

**«Сканер»** — в `/opt/scanner/.env`:

```
AUTH_MODE=platform
PLATFORM_JWKS_URL=http://platform-api:8000/.well-known/jwks.json
PLATFORM_EVENTS_SECRET=<тот же, что SCANNER_EVENTS_SECRET платформы>
VITE_BASE=/scanner/
VITE_API_BASE=/api/scanner
```

Точный список переменных режима платформы — в `docs/integration/scanner.md` для вашей версии «Сканера». `VITE_*` — переменные сборки: фронтенд «Сканера» пересобирается.

```bash
cd /opt/scanner && docker compose up -d --build app web
```

Прямые порты «Сканера» (`SCANNER_WEB_PORT`, `SCANNER_API_PORT`) после перехода не нужны пользователям — оставьте их только на `127.0.0.1` или уберите, чтобы все ходили через шлюз платформы.

**Платформа** — в `/opt/platform/.env`:

```
SCANNER_API_UPSTREAM=http://scanner-app:8000
SCANNER_WEB_UPSTREAM=http://scanner-web:8080
SCANNER_EVENTS_SECRET=<openssl rand -hex 32>
```

```bash
cd /opt/platform && docker compose up -d platform-api gateway
```

Шлюз при старте сгенерирует маршруты `/scanner/` и `/api/scanner/`, а платформа в течение минуты прочитает манифест «Сканера».

## Шаг 6. Проверки

Пройдите все пункты; первый же провал — повод решать, чинить или откатываться.

| # | Проверка | Как | Ожидается |
|---|---|---|---|
| 1 | Платформа видит «Сканер» | «Администрирование → Продукты» или `GET /api/platform/admin/products` | «Сканер», состояние `ok`, версия новой сборки |
| 2 | Вход со старым паролем | обычный пользователь «Сканера» входит на `/login` своим паролем | открывается Главная, есть вкладка «Сканер», карточка «Сканера» с данными |
| 3 | Логин без учёта регистра | войти логином, набранным иначе, чем в «Сканере» (`Sidorova` → `sidorova`) | вход успешен |
| 4 | Проекты | выбор проекта в верхней панели | все проекты «Сканера» с теми же названиями; архивные — в статусе «архив» |
| 5 | История и авторство | во вкладке «Сканер» открыть старый проект и прогон, запущенный этим пользователем | прогон на месте, автор — тот же человек, не «новый пользователь» |
| 6 | Роли | пользователь с ролью `auditor` | может смотреть, не может запускать прогоны |
| 7 | Нет ролей — нет доступа | пользователь платформы без ролей «Сканера» (например, администратор платформы) | вкладки «Сканер» нет; `GET /api/scanner/summary?project=…` с его токеном — `403 no_product_roles` |
| 8 | Без токена | `curl -i https://<платформа>/api/scanner/summary` | `401` |
| 9 | Отключённые | пользователь, отключённый в «Сканере» | войти не может |
| 10 | Выход | меню пользователя → «Выйти» во вкладке «Сканер» | переход на `/login`, вкладки других продуктов тоже требуют входа |
| 11 | Журнал | в БД платформы: `docker compose exec db psql -U platform -c "select time, details from audit_log where action='import.scanner'"` (экран «Журнал аудита» — после шага 2.5 плана) | запись `import.scanner` на каждый запуск с `--apply` |
| 12 | Интеграции | вызовы других систем в API «Сканера» | работают по токену сервисной учётной записи платформы |

## Шаг 7. После перехода

- Задайте пароли пользователям из строки «Без пароля»: «Пользователи и доступ» → пользователь → «Сменить пароль».
- Удалите временного пользователя БД: `DROP ROLE scanner_ro;` (после `REVOKE` его прав) в БД «Сканера».
- Храните `scanner-before.dump`, `platform-before.dump` и `mapping.json`, пока не уверены, что откат не понадобится (рекомендуем 30 дней).
- Управление пользователями и ролями «Сканера» теперь только в платформе. Роли, выданные в интерфейсе «Сканера» до перехода, но после импорта, не перенесены — перезапустите шаг 3 до включения или выдайте их в платформе.

## Откат

Решение откатываться принимается по результатам шага 6. Есть два варианта; почти всегда достаточно первого.

### Вариант А. Вернуть «Сканер» в `local` (данные «Сканера» сохраняются)

Подходит, если сам «Сканер» работает, но что-то не так со входом через платформу, ролями или проектами. Ничего из сделанного в «Сканере» после переключения не теряется.

1. «Сканер»: в `/opt/scanner/.env` вернуть `AUTH_MODE=local`, `VITE_BASE=/`, `VITE_API_BASE=/api` (или просто `cp /opt/backup/migration/scanner.env.before /opt/scanner/.env`), вернуть прямые порты, `docker compose up -d --build app web`.
2. Платформа: в `/opt/platform/.env` очистить `SCANNER_API_UPSTREAM` и `SCANNER_WEB_UPSTREAM`, `docker compose up -d platform-api gateway`. Вкладка «Сканер» пропадает, `/api/scanner/` отвечает 404.
3. Проверка: пользователи входят в «Сканер» по его старому адресу со своими паролями «Сканера».

Почему это безопасно: импорт не трогает таблицу пользователей «Сканера», а локальные пароли в режиме `platform` не удаляются (контракт v1.1, п. 2.5). Заполненный `platform_project_id` режиму `local` не мешает и пригодится при повторной попытке.

Что надо знать:
- пароли, сменённые в платформе после переключения, в «Сканер» не возвращаются — у пользователя снова его старый пароль «Сканера»;
- проекты, созданные в платформе после переключения, остаются в «Сканере» обычными проектами.

Перенесённые пользователи и проекты в платформе остаются. Они не мешают: повторный переход начинается с шага 1, а импорт на шаге 3 повторно ничего не создаст. Если платформу до перехода никто не использовал и нужно вернуть её точно в исходное состояние — восстановите её копию:

```bash
cd /opt/platform
docker compose stop platform-api gateway
docker compose exec -T db dropdb -U platform platform
docker compose exec -T db createdb -U platform platform
docker compose exec -T db pg_restore -U platform -d platform --no-owner < /opt/backup/migration/platform-before.dump
docker compose up -d platform-api gateway
```

Восстановление платформы откатывает **всё**, что в ней сделано после копии, включая пользователей и роли других продуктов.

### Вариант Б. Восстановить БД «Сканера» из копии

Только если повреждены данные «Сканера» (например, при обновлении на шаге 0.1). **Всё, что сделано в «Сканере» после копии на шаге 1, будет потеряно.**

```bash
cd /opt/scanner
docker compose stop web app
docker compose exec -T db dropdb -U scanner --force scanner
docker compose exec -T db createdb -U scanner scanner
docker compose exec -T db pg_restore -U scanner -d scanner < /opt/backup/migration/scanner-before.dump
```

Затем верните прежнюю версию образов «Сканера» и `.env` из `scanner.env.before`, `docker compose up -d`, и выполните пункт 2 варианта А для платформы. Восстановить копию БД под новой версией «Сканера» без отката версии нельзя: её миграции уже рассчитывают на новую схему.

## Репетиция на стенде

Перед работами на настоящей установке процедуру можно пройти на стенде с заглушками:

```bash
dev/scanner-legacy/rehearse.sh          # собирает образы; SKIP_BUILD=1 — без сборки, KEEP=1 — не удалять стенд
```

Скрипт поднимает отдельный compose-проект `platform-migration` (шлюз на `127.0.0.1:28090`) с платформой, заглушками продуктов и учебной БД «Сканера» ([`dev/scanner-legacy/seed.sql`](../dev/scanner-legacy/seed.sql): пять пользователей, в том числе отключённый со старым форматом хэша и логин в другом регистре; три проекта, один архивный; прогоны). Затем проходит шаги 1–6 и откат по варианту А с восстановлением обеих копий, сверяя каждый результат: вход со старым паролем, роли и проекты в токене, 200/401/403 от API «Сканера» через шлюз, перехэширование пароля, идемпотентность повторного импорта, запись в журнале, состояние БД после отката.

Учебную БД можно поднять и на основном стенде: `docker compose --profile fakes --profile migration up -d`, источник для импорта — `postgresql+psycopg://scanner_ro:scanner-ro-pass@scanner-legacy-db:5432/scanner`.

Чего стенд не проверяет: заглушка «Сканера» всегда работает в режиме платформы, поэтому переключение `AUTH_MODE` на ней изображается подключением продукта к шлюзу (`SCANNER_API_UPSTREAM`), а привязку пользователей по п. 2.5 и пересборку фронтенда с `VITE_BASE=/scanner/` нужно проверить на настоящем «Сканере» (шаг 6, пункты 5 и 10).
